===============================================================================
 ISO 27001 ISMS-Portal  —  Kurzdokumentation
===============================================================================

WAS IST DAS
-----------
Eine interne Website (Node/Express), die ISO-27001-Dokumente, Compliance-
Prüfungen und Vorfallbehandlung an einem Ort bündelt. Originaldokumente
(ODT/ODS) werden NICHT direkt angezeigt, sondern in web-freundliche Formate
konvertiert; die Website liest nur die konvertierten Daten.


STARTEN
-------
Voraussetzung: LibreOffice (fuer ODT->PDF Freigaben) + Node.js.

    cd webpages/iso
    npm install
    node server.js
    -> http://localhost:3000

Login ueber /welcome/. Rollen + Passwort werden serverseitig geprueft.
Demo-Passwort: 12345  (ueber Umgebungsvariable ISO_PASSWORD aenderbar).


DATENFLUSS (wichtig)
--------------------
    Originale (docs/*.odt, *.ods)
            |
            v   python converter.py   (manuell ausfuehren)
            |
    docs/conv_markdown/   (*.md   -> Textanzeige, KI-Suche)
    docs/conv_tables/     (*.json, *.csv -> Tabellenanzeige)
    docs/conv_meta/       (*.json -> Metadaten, letzte Aenderung)
            +
    user_data/            (Eingaben aus der WebUI, siehe unten)
            |
            v
    Website fuehrt beim Anzeigen beide Quellen zusammen.

ACHTUNG: converter.py laeuft mit CLEAN_OUTPUTS = True und LEERT die
docs/conv_* Ordner bei jedem Lauf. Alles dort ist generiert und wird
ueberschrieben. Niemals von Hand in docs/conv_* schreiben - es geht verloren.


DATEIEN — WAS DARF MAN BEARBEITEN?
----------------------------------
BEARBEITEN (Quelle, von Hand pflegen):
  docs/*.odt, *.ods .......... Originaldokumente. Danach converter.py laufen
                               lassen, damit die Website die Aenderung sieht.
  config.json ................ Konfiguration: E-Mail-Adressen je Rolle,
                               Vorfallsarten, Systeme, Beteiligte, Routing
                               (wer wird bei welchem Vorfall benachrichtigt),
                               Fristen, Sofortmassnahmen je Szenario, Drive-
                               Links. Reine Konfiguration, KEINE Laufzeitdaten.
  zugriffsverwaltung.json .... Welche Rolle welche Vertraulichkeitsstufe sieht.
  docregister.json ........... Dokumentenliste + Eigenschaften.
  isoschedule.json ........... Pruef-Intervalle fuer den Compliance Monitor.

NICHT VON HAND BEARBEITEN (wird generiert / vom Server geschrieben):
  docs/conv_markdown/  docs/conv_tables/  docs/conv_meta/
                               -> Ausgabe von converter.py, wird ueberschrieben.
  approvals.json ............. Freigabe-Stempel, vom Server geschrieben.
  user_data/incidents.json ... Gemeldete Vorfaelle (WebUI). Server-verwaltet.
  user_data/lessonslearned.json  Lessons Learned (WebUI). Server-verwaltet.

WARUM user_data/ GETRENNT IST:
  WebUI-Eingaben duerfen nicht in docs/conv_* liegen, weil converter.py diese
  Ordner leert. user_data/ liegt ausserhalb und ueberlebt jede Neukonvertierung.
  Diese beiden Dateien legt der Server beim ersten Speichern selbst an.


WICHTIGSTE PROGRAMMDATEIEN
--------------------------
  server.js .......... Express-Backend: Login/Rollen, /api/docs, /api/approve,
                       /api/search, /api/incidents, /api/lessons, /api/measures,
                       /api/sendMail. Serviert die Seiten gefiltert nach Rolle.
  converter.py ....... Office-Dateien -> Markdown/CSV/JSON. Manuell ausfuehren.
  search.js .......... Volltext- und ID-Verknuepfungssuche.
  zerti/index.html ... Hauptseite (Dokumente, Compliance Monitor, SoA,
                       Compliance Workflows, Ueberwachung).
  welcome/index.html . Login-Seite.


COMPLIANCE WORKFLOWS (Vorfall melden / Lessons Learned)
-------------------------------------------------------
Linke Karte "Vorfall melden": Wizard in 4 Schritten (Vorfallsart ->
Entdecker/Beteiligte/Beschreibung -> personenbezogene Daten/Einstufung ->
Systeme). Beim Abschluss berechnet der Server aus config.json die zu
benachrichtigenden Rollen (in Reihenfolge GF -> DevOps -> ISB -> DSB; DSB
automatisch bei personenbezogenen Daten), zeigt Fristen (sofort / 24 h /
72 h / 5 Werktage) und die Sofortmassnahmen des Szenarios. Die E-Mails sind
vorbereitet, bearbeitbar und direkt sendbar (oder lokal per mailto: oeffnen).
Der Vorfall wird in user_data/incidents.json gespeichert.

Rechte Karte "Lessons Learned": Vorfall auswaehlen, Erkenntnisse eintragen,
Korrekturmassnahmen mit Standardmassnahmen-IDs (MAS-...) aus dem Risikoregister
verknuepfen (Verantwortlich, Asset, umgesetzt, erledigt-am). Speichert in
user_data/lessonslearned.json.

Neue Vorfallsart, neuer Empfaenger oder andere Frist?  -> nur config.json
aendern, kein Code.


E-MAIL VERSAND
--------------
/api/sendMail nutzt den nodemailer-Transporter in server.js. Damit echte
Mails rausgehen, oben in server.js die SMTP-Zugangsdaten eintragen
(host/user/pass statt smtp.yourprovider.com). Ohne gueltige Zugangsdaten
funktioniert nur der "Lokal oeffnen" (mailto:) Link.


DOKUMENT-FREIGABE
-----------------
"Direkt freigeben" konvertiert die zugehoerige ODT per LibreOffice zu einer
zeitgestempelten PDF, speichert einen Freigabe-Stempel in approvals.json und
benachrichtigt optional die hinterlegte Rolle. Dafuer muss LibreOffice auf dem
Server installiert sein:  apt install libreoffice
